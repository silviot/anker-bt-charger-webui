Your charger speaks a small, partly encrypted protocol. Here it is, running live.

This page connects to the charger from your browser, runs the handshake, and shows every byte. There is no app, no account and no server. It also has a simulated charger, so you can explore without any hardware.

How it works

A phone or browser talks to the charger in four layers. Each layer solves one problem.

  1. Bluetooth LEMoves bytes. One characteristic for writing, one for notifications.
  2. FramesMark where a message starts and ends, and which command it is.
  3. AES-GCMEncrypts the handshake and every request. The charger's telemetry replies skip it.
  4. TLV fieldsLabel each value inside the decrypted body.

1. Finding the charger

The charger advertises service 0xFF09 and a name that contains its serial number. No Bluetooth pairing is needed. After connecting, a client uses one GATT service:

Service8c850001-0302-41c5-b46e-cf057c562025
Write8c850002-… (write without response)
Notify8c850003-… (replies arrive here)

The charger accepts one connection at a time. If the Anker app is connected, the charger can disappear from scans.

2. The handshake

The first messages use a key that is the same in all units. They exchange identity data, then agree a fresh session key. Watch the steps change as you connect:

  1. 0x0001 Hello Sends the current time.
  2. 0x0003 Parameters Sends fixed parameter values.
  3. 0x0029 Identity The reply has the serial number and firmware.
  4. 0x0005 Setup Sends more fixed values. Their meaning is not documented.
  5. 0x0021 Key exchange Each side sends a temporary P-256 public key.
  6. Session key active From here, all frames use the new key.

This session's key exchange

The session key is bytes 0–15 of the shared secret. The nonce is bytes 16–27. There is no key derivation function. These values exist only in this tab and end with the session.

3. Frames

Every message has the same shape. Multi-byte numbers are little-endian. The last 16 bytes of an encrypted body are the GCM authentication tag. Frames with no encryption flag have no tag.

FF 09 startlength03 00 fixedgroupflags + commandencrypted bodyGCM tagXOR checksum

The high byte of the command also holds two flags: 0x40 means encrypted, and 0x08 means this is a reply. So 48 29 on the wire is an encrypted reply to command 0x0029.

A surprise: on the test unit, the charger sends its 0x0200 replies with no encryption, even after the session key is active. The browser's request is encrypted, but the answer is not. Look at the frame sizes in the Traffic list to see this.

4. Fields and telemetry

A decrypted body is a list of type, length and value items. For the charger's snapshot, each port is a 7-byte structure after a type byte:

A7 08 04 01 E0 4E FB 02 FE 05
  • A7 Port C3 (A5 is C1, A6 is C2)
  • 08 8 bytes follow
  • 04 Value type: raw bytes
  • 01 Mode: active (0 means idle)
  • E0 4E 0x4EE0 = 20192 mV = 20.192 V
  • FB 02 0x02FB = 763 mA = 0.763 A
  • FE 05 0x05FE = 1534 centiwatts = 15.34 W

That example is a real reading from a test A2687. 20.192 V × 0.763 A = 15.41 W, close to the reported value.

Frame lab

Select any frame from the session, or paste one. Then try changing a digit. The XOR checksum detects the change in any frame, and the GCM tag also detects it in an encrypted frame. Telemetry replies have only the checksum, so you can change a reading and the frame still decodes.

      What this says about security

      • Anyone in Bluetooth range can read your port data. This handshake needed no pairing, password or account. It reads voltage, current, power, serial number and firmware. Telemetry replies are also unencrypted on the test unit, so the session key does not protect them.
      • The first key is not secret. It is the same fixed value for every client, and it is public in the projects below.
      • The key exchange has no authentication. Neither side proves who it is, so an attacker in the middle could likely read the encrypted traffic. I did not test this attack.
      • One nonce is used for a whole session. AES-GCM requires a new nonce for each message. Reusing one weakens both its encryption and its tamper detection. The risk here is small, because this data is not very sensitive.
      • Settings need more. Other projects report that an account ID is required for pushed telemetry and settings. I did not test those commands.

      What this page does and does not do

      • It does not change settings. It sends only six commands: 0x0001, 0x0003, 0x0029, 0x0005, 0x0021 and 0x0200. The meaning of some values in 0x0003 and 0x0005 is not documented, but the official handshake uses them too.
      • It leaves out the time zone command. Other clients send 0x0022. It was not needed here, and it could change the charger's state.
      • It polls and does not stream. It asks for 0x0200 once per second. The 0x0300 push stream needs your account ID, according to other projects. A wrong ID can affect the lock-screen image, so this page never sends one.
      • It was tested on one unit. That unit has firmware v0.0.3.7 and a name that starts with ASHDJV. Other projects document ASHDJW and firmware v0.0.5.x. Other firmware can behave differently.
      • Attached-device names are not shown. The test unit's snapshot did not include the fields that identify attached devices.

      If connecting fails

      • Use Chrome, Edge or another Chromium browser on a desktop computer. Firefox and Safari do not support Web Bluetooth.
      • Fully quit the Anker app on your phone, or turn off the phone's Bluetooth.
      • On Linux, if the browser reports that Web Bluetooth is unavailable, enable chrome://flags/#enable-experimental-web-platform-features.
      • On Linux, if scans find nothing and the kernel log shows Opcode 0x2041 failed: -16, restart the adapter: bluetoothctl power off, then bluetoothctl power on.
